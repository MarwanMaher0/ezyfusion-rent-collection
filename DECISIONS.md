## 1. The same paid=true callback twice, 5 ms apart
Both requests go through `handleGatewayCallback` (src/server/services/webhook.ts:133). Each verifies the HMAC (`verifySignature`, :53), checks that the bill exists, and calls `private.apply_gateway_callback` (:112) in one transaction.
The first locks the bill row `FOR UPDATE` (supabase/migrations/20261026000002_money.sql:522). The second blocks on that lock.
The first sees `pending`, sets the bill `paid` (:550), inserts the online payment with `received_at = paid_at` (:555), allocates it and commits.
The second then gets the lock, re-reads the bill, sees `status = 'paid'` (:537) and returns `duplicate`. That is 200 with no effect.
The guarantee is the row lock plus that status check. `payments.gateway_bill_id` is also UNIQUE (20261026000001_schema.sql:155) and the insert in money.sql uses `on conflict do nothing` (:555–564), so even without the lock a second payment for one bill cannot exist.
Tested in tests/webhook/gateway.test.ts: 10 simultaneous deliveries create one payment.

## 2. RM 800 and RM 700 at the same moment, RM 1,000 remaining
Both calls reach `private.record_payment`, which first takes the lease row `FOR UPDATE` (money.sql:107–113, D7). One request, say RM 800, gets the lock. It computes the cap after the lock (:180–188): 1,000 − 0 allocated − 0 pending = 1,000, so RM 800 is accepted as `pending_verification` and commits.
The second request was blocked on the same lease row. READ COMMITTED gives its next statement a fresh snapshot, so its cap is 1,000 − 800 pending = 200, and RM 700 gets P0422, which is HTTP 422.
Because the cap is always computed after the lock, never before, both cannot be accepted, whichever request arrives first. The functions also refuse to run at any other isolation level (D41).
Tested in tests/concurrency/payments.test.ts over HTTP, 5 rounds.

## 3. Every place that works out "today" or converts date ↔ instant
Malaysia is UTC+8 with no daylight saving, so one fixed offset is exact whatever the server or browser zone.
- **Today:** `toMytDate` (src/lib/billing.ts:172) is used by `invoiceStatus` (:178), `overdueCount` (src/server/services/reports.ts:61), the dashboard months (src/app/(app)/dashboard/page.tsx:70) and the tenant's amount due (src/components/tenant/lease-section.tsx:115, `now` set after mount, tenant-portal.tsx:141). The routes pass `new Date()` as `asOf` (src/app/api/leases/[leaseId]/route.ts:9, gateway-bills/route.ts:10). SQL uses `(p_as_of at time zone 'Asia/Kuala_Lumpur')::date` (money.sql:462).
- **Months:** collections group by `received_at at time zone 'Asia/Kuala_Lumpur'` (reports.ts:39).
- **Input:** `parseInstantWithOffset` (src/lib/dates.ts:40) requires an offset; `mytLocalToIso` (:59) reads the form as +08:00; the form's default comes from `formatInstantMyt(new Date())` (leases/[leaseId]/page.tsx:204); the webhook's `paid_at` keeps its own offset (webhook.ts:66).
- **Calendar dates:** `isoDateToDb` (serialize.ts:44) and `dateToIso` (dates.ts:70) use UTC midnight, which is how Prisma represents `date`.
- **Output:** `formatInstantMyt`, `formatMytDisplay` (dates.ts:32, :77).

## 4. Queries not subject to RLS, and what authorizes them instead
- **Prisma connects as `postgres`.** Every route authenticates with `auth.getUser()` (src/server/auth.ts), loads the role from `memberships`/`tenants.user_id` (`loadCaller`, src/server/access.ts:27), then `requireMember`/`requireLeaseAccess`/`requirePaymentAccess` (:37, :60, :66) answer 404 when not visible and 403 for the wrong role. Queries are scoped by the org that check returned.
- **Private plpgsql money functions** run as the owner but re-check the actor (manager/staff of the lease's org, the lease tenant for bills, a manager for decisions). anon and authenticated cannot execute them.
- **SECURITY DEFINER RLS helpers** (schema.sql:330–365) only answer "is the caller a member or tenant?" from `auth.uid()`, with `search_path = ''`.
- **Secret-key Storage client:** slip deletion (payments.ts:50-55) removes only an unreferenced object inside the caller's own org folder; the signed URL (:211-213) runs after `requirePaymentAccess` and uses `slip_path` from the DB row.

## 5. A void reopens invoices while an online payment still has unapplied_sen
Nothing moves automatically. `void_payment` deletes only the voided payment's allocations (money.sql:399) and marks it `voided` (:406). The reopened invoices show as unpaid or overdue again. The other payment's `unapplied_sen` stays as it was.
I chose this because the brief says "Other payments' allocations do not change". Re-applying the credit would change another payment's allocations without anyone deciding to (D14, D37).
It also keeps a void predictable and auditable: the `payment.voided` audit row records exactly what was released, and nothing else changes. Staff can see both the reopened balance and the credit on the lease page. Applying credit to reopened invoices would be an explicit, audited manager action, which I would add next.
